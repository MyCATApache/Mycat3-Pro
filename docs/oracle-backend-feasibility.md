# 后端 Oracle 接入可行性评估（rust-oracledb 方案）

> 评估日期：2026-10-17 · 结论：**可行且成本显著低于 TNS 前端方案**（约 3–5K 行 vs 6–10K 行），
> 协议层风险归零（官方驱动负责），真正的成本在 **MySQL→Oracle SQL 方言翻译**。
> 建议：若有 Oracle 数据访问需求，**先做后端接入**；其中执行层抽象与测试基建可复用于未来的 TNS 前端。

## 0. 一句话结论

用官方 [oracle/rust-oracledb](https://github.com/oracle/rust-oracledb)（crates.io `oracledb`
26.0.0-beta，**UPL-1.0 OR Apache-2.0 双许可**，纯 Rust thin 驱动，免 Oracle 客户端库）作为后端
访问层，让 Mycat3 Pro 的 **MySQL/PostgreSQL/TDS 三种前端协议都能查询 Oracle 数据库**——
这一方向把"协议猜测代价与漏洞"完全外包给了 Oracle 官方维护的驱动，工程上可行；
剩余工作集中在结果模型映射与 SQL 方言翻译（~3–5K 行），风险点是驱动尚处 beta 与
方言翻译的长尾。

## 1. 场景矩阵：两个"Oracle 接入"方向对比

| 方向 | 用户场景 | 协议角色 | 协议成本 | 方言成本 |
|---|---|---|---|---|
| **A. TNS 前端**（上一份报告） | Oracle 工具（sqlplus/ojdbc/DBeaver/DBLINK）管理 Mycat 分片集群 | 服务端（自研 TNS/TTC server） | 高（6–10K 行，四层协议） | 无（转发 SQL 到 MySQL 后端） |
| **B. Oracle 后端**（本报告） | MySQL/PG/TDS 客户端查询 Oracle 库（联邦查询/迁移/统一工具链） | 客户端（官方 rust-oracledb） | **≈0**（驱动全包） | **中**（3K 行量级 MySQL→Oracle 翻译） |

两者互补而非互斥。方向 B 是"访问 Oracle 数据"最典型的真实需求，且可以复用方向 A 需要的
执行层抽象与 `gvenzl/oracle-free` 测试基建。**如果目标是降低协议猜测代价：方向 B 是正解**。

## 2. 驱动核实结果（2026-10 docs.rs / GitHub 核验）

| 项 | 结论 |
|---|---|
| 版本/成熟度 | `oracledb 26.0.0-beta.4`（2026-06 首发，官方持续迭代）。**beta 状态是主要风险**：API 可能变动 → 用版本锁定 + 自建薄封装隔离 |
| 许可 | UPL-1.0 OR Apache-2.0（含专利授权条款），可安全集成与分发（保留声明） |
| 连接方式 | `Config::new().set_connect_string(...).set_user(...).set_password(...)`；连接串为 Oracle Easy Connect 形式（`host:port/service_name`）——可从现有 `jdbc:oracle:thin:@//host:port/service` 的 JDBC URL 解析映射 |
| 查询 API | `Connection::query/execute/execute_batch` + `BindParameters` 绑定变量；`Row`/`Value`/`OracleNumber`/`OracleTimestamp`/`Lob` 类型化结果；`ExecResult`（DML 影响行数） |
| 事务 | autocommit/commit/rollback 齐全（本地代理事务与 SAVEPOINT 转发可平移复用） |
| 连接池 | 内置 `Pool`/`create_pool`/`acquire`（可取代/并行于自研池） |
| TLS | rustls 支持（tcps）；**ANO（Oracle Native Network Encryption）不支持**（`NSI_NA_REQUIRED → todo!()`）——与 Pro 现网 MySQL 客户端"无 TLS/无压缩"的立场一致；对 `ENCRYPTION_SERVER=REQUIRED` 的加固 Oracle 实例无法连接，需文档明确 |
| 依赖 | aes/cbc/pbkdf2/sha2/rustls/chrono 等常规密码学栈；可选 arrow（我们不需要）→ 二进制体积增加可控 |

## 3. 架构改造点（按依赖顺序）

```
Mycat3 Pro 现状                          Oracle 后端接入后
─────────────────────────               ─────────────────────────
executor ──► client::CheckedOutConn     executor ──► trait BackendConn
            (MySQL 原始载荷透传)                     ├─ MySqlBackend（现状，快路径保留）
                                                     └─ OracleBackend（rust-oracledb，
                                                        结果转字符串行 → engine 解析路径）
datasource.url (jdbc:mysql://...)       + jdbc:oracle:thin:@//host:port/service 解析
heartbeat (select 1 / show slave status)+ select 1 from dual（SINGLE_NODE 语义）
ddl.rs 物理建表 (MySQL DDL)              Oracle 后端物理 DDL 改为手工/方言生成（见 §5）
```

1. **数据源配置扩展**（~150 行）：`DatasourceConfig.dbType` 字段早已存在（当前被忽略），
   启用之；新增 JDBC Oracle URL 解析（`jdbc:oracle:thin:@//host:port/svc` → connect string）。
2. **后端连接抽象**（~400 行）：定义 `trait BackendConn { async fn query(&mut self, sql) ->
   Result<BackendOutcome> }`，`BackendOutcome = Ok{affected} | Rows{columns, rows}`（与
   `engine::EngineOutcome` 同构）。executor 的三条路径：
   - MySQL 单任务 SELECT 快路径（原始载荷透传）**保留不动**；
   - Oracle 后端一律走"解析路径"（同多分片归并路径）：rust-oracledb 类型化 `Row` →
     `Vec<Vec<Option<String>>>`（OracleNumber/Timestamp 按可读格式 stringify）；
   - 归并（ORDER BY/LIMIT/COUNT 等）在字符串行模型上工作，**与方言无关**，零改动。
3. **连接池**（~300 行）：优先直接使用驱动的 `Pool`（min/max、空闲回收），包装进
   `ConnectionManager`；broken 连接剔除、事务连接不回池等语义沿用现有 `TransactionSession`。
4. **方言翻译层**（~1500–3000 行，真正的成本中心，见 §4）：在 `sql` crate 中增加
   `dialect` 子模块：sqlparser AST → 目标方言 AST/文本。位置在路由重写之后、任务下发之前
   （`BackendTask { target, sql }` 携带方言标记，executor 按数据源 dbType 选择）。
5. **心跳/管理适配**（~200 行）：Oracle 心跳 SQL 改 `select 1 from dual`；
   `show slave status` 等 MySQL 特有探测对 Oracle 数据源禁用（SINGLE_NODE 语义）；
   活跃计数/BalanceLeastActive 不变。
6. **测试基建**（~500–1000 行）：`docker run gvenzl/oracle-free`（23ai Free）+ 集成测试
   （配置 oracle 数据源 → DDL 手工建物理表 → MySQL/PG/TDS 三前端查询 + 分片路由验证）。

## 4. MySQL→Oracle 方言翻译规则目录（核心风险清单）

sqlparser(MySQL) AST → Oracle 12c+ 文本。逐条给出规则与风险评级：

| # | MySQL 语法 | Oracle 等价 | 风险 |
|---|---|---|---|
| 1 | `LIMIT n [OFFSET m]` | `OFFSET m ROWS FETCH NEXT n ROWS ONLY`（12c+） | 低（AST 有 limit/offset 字段，纯重写；注意 LIMIT 出现在子查询/UPDATE 的语法差异） |
| 2 | 反引号标识符 `` `t` `` | 双引号 `"t"`（保留大小写） | 低 |
| 3 | `INSERT INTO t VALUES (1,'a'),(2,'b')` | `INSERT ALL INTO t VALUES (1,'a') INTO t VALUES (2,'b') SELECT 1 FROM DUAL` | 中（我们分片 INSERT 拆行后恰是逐行，可简化） |
| 4 | `IFNULL(a,b)` / `NOW()` / `CURDATE()` | `NVL(a,b)` / `SYSTIMESTAMP` / `TRUNC(SYSDATE)` | 中（函数名映射表，覆盖常用集） |
| 5 | `AUTO_INCREMENT` DDL | `GENERATED BY DEFAULT ON NULL AS IDENTITY`（12c+） | 中（物理 DDL 方言化） |
| 6 | `SHOW ...` / `USE db` | 本地层已拦截（show/use 不进后端） | 无 |
| 7 | 大小写语义 | Oracle 未加引号标识符自动大写；我们统一加双引号保名 | 低 |
| 8 | 类型字面量/日期 `'2026-01-01'` | 字符串与 DATE 隐式转换差异 → 改写为 `DATE '2026-01-01'` | 中 |
| 9 | `UPDATE t SET ... ORDER BY ... LIMIT` | Oracle 不支持 → 报"不支持"（文档化） | 低（明确报错） |
| 10 | 分片条件字面量（=、IN、BETWEEN、>） | 语法共通，无需翻译 | 无 |

关键架构决策：**翻译层只管"语法形状"，不管语义**（与 Java 版 jOOQ parsingDataSource
的定位一致）——翻译不了的结构明确报"方言不支持"，绝不静默产生错误语义。这使长尾可控。

## 5. 明确不做的部分（文档化边界）

- ~~DDL 自动化对 Oracle 后端~~（已实现）：逻辑 `CREATE TABLE` 生成 Oracle 类型映射、
  identity、索引与幂等 PL/SQL；`DROP TABLE`/`repairPhysicalTable` 同步支持。视图 DDL 仍
  仅支持 MySQL，对 Oracle 显式报错而不是静默跳过。
- **ANO 加密**：rust-oracledb 不支持；`ENCRYPTION_SERVER=REQUIRED` 的实例不可接入（TLS
  端口可行）。文档明确。
- **XA**：维持本地代理事务（跨 MySQL+Oracle 混合事务不保证原子性）。
- 序列/分片算法/广播/归并语义：与后端方言无关，全部直接复用。

## 6. 工作量与风险总结

| 项 | 估算 | 风险 |
|---|---|---|
| 驱动集成 + 池 | 500–800 行 | 低（API 稳定部分） |
| 执行层抽象 | 300–500 行 | 低 |
| 方言翻译层 | 1500–3000 行 | **中（长尾）**，靠 §4 边界策略收敛 |
| 心跳/管理适配 | ~200 行 | 低 |
| 集成测试（oracle-free 容器） | 500–1000 行 | 低 |
| **合计** | **≈3–5K 行** | |

风险排序：
1. **beta 驱动 API 变动** → 锁定版本 + 薄封装隔离（自研 `oracle_backend.rs` 单点依赖）；
2. **方言翻译长尾** → 只承诺 §4 列表内语法，其余明确报错；
3. **加固实例（ANO REQUIRED）不可达** → 文档声明 + 支持 TLS 端口；
4. 结果模型为字符串化（数值精度/时间格式）→ 文档声明（与 PG/TDS 前端同一策略）。

## 7. 建议

**若存在 Oracle 数据访问诉求（联邦查询、迁移、统一 BI 工具链），推荐实施方向 B**：
- 成本约为 TNS 前端（方向 A）的一半，协议风险为零（官方驱动），且交付的是最主流的
  "用 MySQL 生态工具查 Oracle"场景；
- 执行层抽象、`oracle-free` 测试基建、方言层均可在未来立项方向 A 时直接复用（方向 A 的
  Phase 0 差分实验台与本方向的测试容器是同一个）；
- 实施顺序建议：① 执行层抽象（回归零风险）→ ② 驱动集成 + 池 + 心跳 → ③ 方言翻译层
  （逐条点亮 §4 规则，每条配测试）→ ④ 三前端联调验收。

验收标准：`gvenzl/oracle-free` 容器上建分片物理表后，
`mysql/psql/sqlcmd 任一客户端 → Mycat3 Pro → Oracle` 完成
`insert/select where 分片键/count 归并/事务 begin-commit`，结果与直连 Oracle 一致。

## 8. 实施结果（2026-10，方向 B 已落地）

按 §7 顺序实施完成，全部验收标准已通过：

| 交付 | 内容 |
|---|---|
| `crates/oracle` | rust-oracledb 26.0.0-beta.4 thin 驱动封装：阻塞式自研连接池（Mutex 空闲队列 + 信号量、`spawn_blocking` 隔离阻塞调用）、`PooledOracleConn`/`DetachedOracleConn`、结果渲染为字符串行模型（NUMBER→OracleNumber、TIMESTAMP→去尾零、BLOB→`\x`十六进制）、JDBC URL 解析、`select 1 from dual` 心跳 |
| 执行层 | `BackendPool`（MySql/Oracle 枚举）按 dbType 分派；`BackendSession` 统一 `query/set_forward/tx_command`；结果合成 MySQL 文本行载荷，归并/透传/三前端回写零改动 |
| 方言翻译 | `crates/sql/src/oracle.rs`（14 单测）：标识符双引号（内建名跳过）、LIMIT→ROWNUM 包装、多行 INSERT→`INSERT ALL`、函数映射（IFNULL→NVL、NOW→裸 `CURRENT_TIMESTAMP`、DATE_FORMAT→TO_CHAR、GROUP_CONCAT→LISTAGG 等）、`%-` 日期格式转换；不可翻译结构显式报错 |
| 事务语义 | 事务外语句即时 COMMIT（对应 JDBC autocommit=true；驱动默认 autocommit=false 已收口）；事务内连接按数据源固定、COMMIT/ROLLBACK 走驱动接口、SAVEPOINT 直传；连接归还池时回滚净化 |
| TDS 适配 | T-SQL `SELECT [ALL\|DISTINCT] TOP (n)` → `LIMIT n`（多语句批中 LIMIT 归属首语句；PERCENT/WITH TIES 不重写） |

**集成验证**（`container-registry.oracle.com/database/free:latest` 容器 + MySQL 8 容器，
`PartitionByMod count=2` 混合分片，MySQL/Oracle 各一片）：三种前端客户端
（mysql CLI / psql / sqlcmd）均可对混合表完成：混合多行 INSERT（按行拆分发往两个后端，
`now()`/`current_timestamp` 均正确落库）、跨后端归并 `order by`/`limit`/`count`、
跨后端 `update`/`delete`、事务 `begin-commit`/`begin-rollback`（含落在 Oracle 节点的行）、
`SET autocommit=0` 隐式事务；Oracle 物理表行数与逻辑视图逐行核对一致。

2026-10 增补：Oracle 物理建表已自动化（`translate_oracle_ddl`：`NUMBER/VARCHAR2/CLOB/BLOB/
TIMESTAMP`、`AUTO_INCREMENT`→identity、`KEY`→`CREATE INDEX`、幂等 PL/SQL；逻辑 `CREATE TABLE`
→ 自动建 schema/表/索引，`DROP TABLE`/`repairPhysicalTable`/`RENAME TABLE` 均按 Oracle 方言执行）。
实测（Oracle Free 23ai，用户 MYCAT）：自动建表、identity、索引、单行插入、删表、重命名、
配置热更新均通过；多行 identity INSERT（INSERT ALL）仍存在 Oracle 侧 identity 分配差异，
建议显式提供主键或逐行插入。

遗留边界：视图物理 DDL 仍仅支持 MySQL（Oracle 显式报错）；ANO 原生加密不可达（TLS 可用）；
跨后端混合事务不保证原子性（无 XA）。
